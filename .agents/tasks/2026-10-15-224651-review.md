# Nova regra de score — página dedicada com preview em tempo real

Substitui o fluxo de criação/edição via modal em `AnaliseScore` por duas rotas dedicadas (`/analise/score/nova` e `/analise/score/:id/editar`) que renderizam `ScoreRulePage`. Ao lado do formulário, `ScorePreviewPanel` avalia a regra em construção contra os fundamentos da carteira ativa em tempo real. As novas rotas são declaradas como irmãs do grupo `analise` para não herdar o layout de tabs da `AnalisePage`.

Watch for: o toggle "Score existente" não limpa o campo `name` ao ser acionado enquanto o modo "Criar novo score" estava preenchido — um `name` residual pode passar na validação silenciosamente (**confirmed**). O `ScorePreviewPanel` tem largura fixa de 420 px sem `overflow-x: hidden` no container pai, o que pode causar scroll horizontal em viewports menores que 420 px (**likely**).

**Verdict**: NEEDS_CHANGES

---

## High-level view

As rotas são declaradas corretamente fora do grupo `<Route path="analise" element={<AnalisePage />}>`, garantindo que a `ScoreRulePage` ocupe o `<Outlet />` do `AppShellNovo` sem herdar as tabs de navegação da análise. A ordem `analise/score/nova` antes de `analise/score/:id/editar` evita o conflito de parâmetros.

O formulário usa `react-hook-form` com `zodResolver(scoreRuleSchema)` e alimenta o `ScorePreviewPanel` via `watch()` em todos os seis campos. A validação Zod cobre o caso `between` com `superRefine`. O payload enviado zera `threshold_max` quando o operador não é `between`, alinhado com o schema.

O toggle "Score existente / Criar novo score" controla qual elemento de entrada preenche `name`, mas os dois caminhos não compartilham o estado do campo: ao mudar de modo, o valor anterior persiste no `register('name')` sem ser limpo. Isso permite que um nome digitado em "Criar novo score" permaneça quando o usuário muda para "Score existente" e não seleciona nada no `<select>`, o que passaria a validação de `name: z.string().min(1)` com o valor fantasma.

A largura fixa `w-[420px]` é declarada diretamente no container raiz do `ScorePreviewPanel`. `ScoreRulePage` envolve o painel com `w-full md:w-auto`, mas esse wrapper não sobrescreve a largura interna — o resultado é que em viewports abaixo de 420 px o painel causará scroll horizontal mesmo no breakpoint mobile.

<details>
<summary>Issues (2)</summary>

1. **Name residual no toggle de modo** — Ao mudar de "Criar novo score" para "Score existente" (ou vice-versa), o valor de `name` não é limpo com `setValue('name', '')`. Um usuário pode digitar um nome, voltar para "Score existente", não selecionar nada, e submeter com `name` preenchido pelo valor anterior — a validação Zod passa e uma regra com nome não pertencente a nenhum score existente é criada silenciosamente. Adicionar `setValue('name', '')` no handler de clique do toggle em ambas as direções.

2. **ScorePreviewPanel com largura fixa em viewports estreitos** — O painel tem `w-[420px]` declarado no próprio componente (`<div className="bg-[#1B1B1B] ... w-[420px] flex-shrink-0">`). No mobile, `ScoreRulePage` wrapa o painel com `w-full md:w-auto`, mas como `w-[420px]` está dentro do próprio `ScorePreviewPanel`, a largura interna fica fixada em 420 px mesmo quando o container externo é `w-full`. Isso causará overflow horizontal em telas menores que 420 px. A largura fixa deveria ser aplicada apenas no breakpoint `md` (ex: `w-full md:w-[420px]`) dentro do componente.

</details>

### Toggle "Score existente / Criar novo score" não limpa o campo name

O estado `scoreMode` controla qual elemento de entrada é renderizado, mas os dois caminhos compartilham o campo `name` do `useForm`. Quando o modo é `'existing'`, o campo é controlado via `setValue('name', e.target.value)`. Quando o modo é `'new'`, o campo é controlado via `register('name')`. A troca de modo não invoca `setValue('name', '')`, portanto o valor preenchido em um modo persiste invisível quando o outro modo é exibido.

Cenário concreto: o usuário digita "Score Teste" em "Criar novo score", muda para "Score existente", vê o select com `value=""` (placeholder "Selecione um score…"), não seleciona nada, e clica em "Criar regra". O campo `name` ainda tem "Score Teste" em seu estado interno — a validação `z.string().min(1)` passa, e a regra é criada com `name: "Score Teste"` sem o usuário perceber. A correção é adicionar `setValue('name', '')` nos dois handlers do toggle:

```tsx
onClick={() => { setScoreMode('existing'); setValue('name', '', { shouldValidate: false }) }}
onClick={() => { setScoreMode('new'); setValue('name', '', { shouldValidate: false }) }}
```

### Largura fixa do ScorePreviewPanel em mobile

`ScorePreviewPanel` declara `w-[420px] flex-shrink-0` diretamente no seu container raiz. `ScoreRulePage` envolve o painel com `<div className="w-full md:w-auto">`, mas esse wrapper externo não sobrescreve a largura interna do componente — Tailwind gera classes independentes e o componente filho "ganha" com `w-[420px]` porque está mais próximo do elemento no DOM. O resultado é que em qualquer viewport abaixo de 420 px, o painel forçará scroll horizontal. A solução é mover a largura fixa para o wrapper externo em `ScoreRulePage` e tornar o container interno do `ScorePreviewPanel` `w-full`:

No componente: `<div className="bg-[#1B1B1B] border border-white/[0.08] rounded-[14px] p-6 w-full flex-shrink-0">`  
No wrapper em `ScoreRulePage`: `<div className="w-full md:w-[420px] flex-shrink-0">`
