- (decision by user) Paradigma: monolito modular com módulos como pastas organizacionais. Separação clara de código por domínio (auth, portfolio, score, etc.) sem boundaries rígidas entre módulos. Pragmático para MVP, permite importação livre entre módulos.
- (decision by user) State management: Zustand para store global. Minimalista, menos boilerplate que Redux, fácil de testar. Adequado para complexidade do MVP.
- (decision by user) Data fetching: TanStack Query (React Query) + Supabase Client para queries e mutations (cache automático, loading/error states). Supabase Realtime subscriptions seletivas para casos específicos (ex: alertas novos). Combinação oferece cache robusto + UX reativa onde justifica.
- (decision by user) Cálculos híbridos: apresentacionais no cliente (soma patrimônio, ordenação, filtros), lógica de negócio no servidor (Score Fundamentalista, Preço-Teto Bazin, geração de alertas, preço médio ponderado de transações). Server-side via Supabase Edge Functions ou Postgres Functions. Equilibra velocidade de dev MVP com consistência e preparação para escalar.
- (decision by user) RLS Strategy: tabelas privadas (positions, transactions, score_rules, alerts, user_preferences) com RLS ativo (policy user_id = auth.uid()). Tabelas públicas/compartilhadas (assets, price_history, dividends, fundamentals, benchmarks) sem RLS - dados de mercado são públicos. Backend/service role insere dados compartilhados. Mais pragmático e performático que RLS em tudo.
- (decision by user) Estrutura frontend: módulos autocontidos. src/modules/{nome}/ contém components/, hooks/, services/, types/ do módulo. src/shared/ para código reutilizável. Clara navegação por domínio, escalável, alinhada com paradigma de módulos organizacionais.
- (decision by user) Modelagem de dados: Posições como tabela independente (positions) - usuário pode cadastrar diretamente ou via transações. Transações (transactions) opcionais, quando existem recalculam preço médio da posição. Score Fundamentalista e Preço-Teto calculados on-demand sem persistir resultado - adequado para MVP com dados seed, pode cachear depois se necessário.
- (decision by user) Deploy: Railway ou Render para frontend (Vite build) + eventual backend Node/workers. Supabase Cloud para database/auth/edge functions. CI/CD via GitHub Actions. Mais flexível que Vercel puro, mantém simplicidade para MVP. Ambientes: production + staging (Supabase permite projetos separados).
- (event) Spine distilada: 10 ADs, stack técnica com versões atuais, 11 tabelas de schema (6 privadas RLS + 5 públicas), estrutura de módulos, 3 diagramas mermaid, divisão cliente-servidor.
- (event) Reconciliação PRD concluída: 10 gaps arquiteturais (4 críticos: performance strategy, AwesomeAPI integration, local dev setup, jobs on-demand; 3 médios: testing, migrations, password recovery; 3 menores: observability, browser compat, security details). Score 7.5/10.
- (decision) AD-11 Performance Strategy: Postgres indexes em (user_id, ticker, created_at). Queries limitadas a 50 posições MVP. Gráficos lazy-load com React.lazy. TanStack Query staleTime 5min para dados que mudam pouco (fundamentals, dividends). Target: <2s carteira, <3s gráficos.
- (decision) AD-12 AwesomeAPI Integration: Client-side fetch via TanStack Query com staleTime 1h (taxa USD muda devagar). Fallback para taxa fixa R.00 se API falhar. Endpoint: awesomeapi.com.br/json/last/USD-BRL. Sem cache server-side no MVP (overhead desnecessário).
- (decision) AD-13 Local Dev Setup: Supabase Cloud para dev (projeto separado de production). Vite dev server local. .env.local com VITE_SUPABASE_URL e VITE_SUPABASE_ANON_KEY do projeto dev. Seed scripts SQL para popular dados mock. Docker opcional, não obrigatório para MVP.
- (decision) AD-14 Alertas On-Demand: Botão 'Atualizar Alertas' na tela de Alertas dispara Supabase Edge Function (POST /functions/v1/generate-alerts). Function varre positions e transactions do user, gera alertas, insere na tabela alerts. Cliente refetch via React Query após success. On-demand no MVP, cron daily em v2.
